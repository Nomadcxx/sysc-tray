# sysc-tray v0.1 Implementation Plan

> **For Claude:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task.

**Goal:** Ship the StatusNotifierItem and DBusMenu daemon, its exported shell protocol, and the release
gates required by sysc-shell Milestone 5.

**Architecture:** The service owns watcher/host policy, item generations, property refresh, DBusMenu
revisions, and method calls. One state owner serializes D-Bus results into immutable snapshots and
deltas. The exported standard-library-only `protocol` package uses bounded framed JSON; sysc-shell owns
theme lookup, rasterization, layout, surfaces, root chains, and preferences.

**Tech Stack:** Go 1.26, `github.com/godbus/dbus/v5`, StatusNotifierItem, StatusNotifierWatcher,
DBusMenu, Unix sockets, four-byte length-prefixed JSON.

**Specs:**
- `docs/plans/2026-08-27-sysc-tray-design.md`
- sysc-shell `docs/plans/2026-08-31-notifications-and-tray-integration-design.md`

---

## Global constraints

- Track items by unique bus owner, object path, and service generation.
- Keep D-Bus working with no shell connected. One presenter may connect.
- Export protocol types from this module; the package must import only the standard library.
- Bound item, menu, string, pixmap, queue, and update work before allocation or copying.
- One malformed item, menu, or pixmap cannot remove a healthy sibling.
- The service sends renderer-neutral state. It does not import shell UI types or rasterize SVG.
- The shell owns show/hide, pinning, order, overflow, menus as surfaces, tooltip surfaces, and root state.
- Never retry Activate, SecondaryActivate, Scroll, menu selection, or AboutToShow after an unknown result.
- Tag `v0.1.0-rc.1` before shell integration and `v0.1.0` after live qualification.
- Release commits contain no local `replace` directive.

### Fixed bounds

| Resource | Limit |
|---|---:|
| Items | 128 |
| Pixmap | 512 × 512, 2 MiB per item, 8 MiB aggregate |
| Menu | depth 8, 512 nodes, 2 MiB icon data |
| Tooltip text | 2 KiB flattened by shell |
| Wire frame | 16 MiB |
| Presenter queue | 256 messages / 32 MiB decoded |
| Property changes | 30 Hz per item / 120 Hz service-wide |

### Task 2: Watcher and canonical item identity

**Files:**
- Create: `internal/watcher/server.go`, `internal/watcher/attach.go`, `internal/watcher/address.go`
- Test: `internal/watcher/server_test.go`, `internal/watcher/attach_test.go`

**Step 1: Write failing private-bus tests**

Under `dbus-run-session`, cover:

- acquire and export `org.kde.StatusNotifierWatcher` when no owner exists;
- attach as a host to a healthy existing watcher instead of fighting for the name;
- register the service's host identity once;
- accept item registration by service name or object path;
- resolve the sender's unique owner and canonical object path;
- reject malformed paths and unowned well-known names;
- owner replacement removes the old generation before adding the new one;
- watcher loss enters a bounded reacquire/attach path without a name-acquisition loop;
- bus reconnect rebuilds watcher, host, items, and subscriptions in order.

Canonical identity:

```go
type Key struct {
	Owner      string
	ObjectPath dbus.ObjectPath
	Generation uint64
}
```

Never key an item by reusable well-known name alone.

**Step 2: Implement watcher policy**

If the watcher name is free, acquire it and implement its registration methods, properties, and signals.
If a healthy owner exists, call `RegisterStatusNotifierHost`, read
`RegisteredStatusNotifierItems`, and subscribe to registration/unregistration signals. Resolve all
addresses through the bus daemon before publishing them to state.

Use a capped reconnect backoff with cancellation. A healthy external watcher remains authoritative.

